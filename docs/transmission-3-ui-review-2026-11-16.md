# Transmission 3.00 与当前 UI 的封板前评估

评估日期：2026-11-16（Asia/Shanghai）。范围按用户最新要求收敛为：3.00 接入当前 UI 后，显示、保存与操作是否符合真实含义。不讨论接口覆盖率，不以其他版本的表现代替 3.00，也不扩展到部署平台或旧浏览器验收。

被审查的现有静态版本：SHA-256 `cf927e7a81040fcd1b2b2cfdd030d9167787549ea61aa1872da8504ea9e0c179`。本轮没有修改业务代码或发布环境。

## 判断

**3.00 可以继续使用这套 UI，日常使用路径没有发现必须升级 daemon 或放弃 UI 的整体性障碍；但当前实现还不宜直接作为无保留的封板版本。** 需要优先处理下列操作身份、统计含义和 Tracker 保存行为。多数问题是 UI 自身的实现边界，不是 3.00 整体不兼容。

任务配置 tab 已按用户条件移除。此前 `seedIdleLimit=0` 返回 success 但回读不变的观察，不再是当前这个已删除页面的阻断项，也不能据此宣称 3.00 所有配置都不能用。现存工具栏限速仍需单独审查，见第 5 项。

## 具体问题

### 1. 高优先级：任务 ID 被复用时，勾选可能落到另一任务

- 触发条件：一次刷新直接拿到“相同数字 ID、不同 hash”的任务，且没有经过会清空选择的 `connect()`。
- 当前行为：`refresh()` 只检查勾选 ID 是否还存在。原勾选继续保留；之后点击工具栏时，`targets()` 捕获的是新任务的 hash。
- 影响：用户原来勾选 A，刷新后同 ID 对应 B，再点击暂停、校验等按钮，可能操作 B。已经打开确认框后冻结的旧 hash 有保护，但不能保护“勾选后、打开确认框前”这一阶段。
- 证据：受控 store 复现 A04：勾选 ID=1/old-hash，刷新到 ID=1/new-hash，`checkedIds` 仍为 `[1]`，新捕获目标为 new-hash。未向实际任务发送命令。
- 建议：比较刷新前后的 ID/hash；身份变化时清除该行勾选及详情，或从勾选时起保存 hash 身份。
- 位置：`src/stores/app.ts:228`、`:235`、`:348`；`src/domain/torrents.ts:180`。

### 2. 高优先级：跳过文件时，“已完成大小”会高估

- 当前列表及概览使用 `totalSize - leftUntilDone`。3.00 中 `leftUntilDone` 是所选文件还需下载的数据量，不能直接从整个种子的总大小相减。
- **本轮真实 3.00 实测**：自建两个各 16,384 字节的文件；只保留并完成第一个，第二个跳过且没有数据。daemon 返回 `totalSize=32768`、`sizeWhenDone=16384`、`leftUntilDone=0`、`haveValid=16384`、`haveUnchecked=0`、`percentDone=1`。当前 UI 算法却得到已完成 32768 字节。
- 影响：实际只有 16 KB，却显示已完成 32 KB；文件列表和分块图可以与列表/概览数字对不上。这是沿用旧公式的语义问题，不是 3.00 返回错误。
- 建议：明确口径。若表示已选任务完成量，用 `sizeWhenDone - leftUntilDone`；若表示整个种子当前实际持有的数据，则使用对应真实持有量字段，不混用两种口径。
- 来源：[3.00 上游字段定义](https://raw.githubusercontent.com/transmission/transmission/3.00/libtransmission/transmission.h)，`tr_stat.sizeWhenDone/leftUntilDone/haveValid/haveUnchecked`。
- 位置：`src/domain/torrents.ts:181`；`src/components/DetailPane.vue:254`。

### 3. 中优先级、3.00 特有：Tracker 只改分组时保存不生效

- 服务器编辑框使用空行表示 tier。3.00 分支实际只生成新增、删除、替换 URL 的命令，不处理单独 tier 调整。
- 触发：URL 不变，只合并或拆分空行分组。`updateTrackers()` 正常返回，弹框关闭，实际上没有发送任何 `torrent-set`。
- 影响：用户认为已保存，重新打开却恢复原分组。批量替换 URL 的正常路径不等于这个分组编辑路径也正常。
- 证据：受控 store 复现 A03；3.00/RPC16 分支，两个 URL 从不同 tier 改为同 tier，写请求数为 0。该问题由实际前端分支确认，不需要假定 daemon 会如何处理一个根本没发送的请求。
- 建议：在 3.00 下明确禁止不支持的 tier 编辑并说明原因，或另行实现经过真实验证的转换；不能无操作却按保存成功处理。
- 位置：`src/stores/app.ts:450`；`src/components/DetailPane.vue:338`。

### 4. 中优先级：Tracker 冲突检查缺少分组身份

- 当前编辑冲突只比较 URL 数组，忽略 tier 和 ID。
- 若另一客户端调整了同一批 URL 的分组，当前页面无法识别这个变化。3.00 更改 URL 时还会使用编辑开始时保留的 ID；不能仅凭 URL 相同就认定编辑基线完全一致。
- 证据边界：代码可确认比较对象缺少 tier/ID；A05 在 RPC17 的整表写入分支复现覆盖其他客户端 tier 的结果。**不把该 RPC17 结果描述为已复现的 3.00 tier 覆盖。** 对 3.00 的结论是编辑基线检查不足，具体 ID 变化需要相应条件才触发。
- 建议：基线比较完整的 URL/tier/ID，写入使用刚回读的有效身份，并提示用户重新载入冲突数据。
- 位置：`src/stores/app.ts:434`；`src/components/DetailPane.vue:329`。

### 5. 中优先级：限速弹框默认值容易误导，并会一并覆盖上下行

- 弹框每次初始化为上下行都启用、各 100，不从任务读取当前值。保存时四个字段一起提交。
- 影响：用户以为显示的是现有配置，仅想调整下载，却可能同时把原本不限速的上传改成 100；多任务各自配置也会被统一覆盖。
- **本轮真实 3.00 实测**：四个限速字段提交 100 后可正确读回，说明此处问题是 UI 的默认值和提交含义，而不是 3.00 不支持限速。这个读回不代表真实流量的限速吞吐测试。
- 建议：单任务加载真实值；多任务用“保持不变/统一设置”的明确语义，只提交用户指定修改的方向。
- 位置：`src/components/ActionDialog.vue:36`、`:77`。

### 6. 中优先级：部分统计会把未知值显示成真实 0

- 列表已经能用 `—` 区分未知；概览中的种子数、下载人数等仍有 `?? 0`。3.00 的 Tracker scrape 尚无结果或失败时，不应被解读为站点确实没有种子。
- 影响：列表可能显示 `—`，同一任务概览却显示 `0`；用户据此判断无源会产生偏差。
- 建议：概览与列表共用未知值规则。文件优先级等缺失值也应避免无条件当成正常值。
- 位置：`src/components/DetailPane.vue:260`、`:263`；对照 `src/domain/table.ts` 的 `peerCount()`。

### 7. 中优先级：多个 Tracker 的人数相加不是去重后的真实人数

- `normalizeTorrent()` 将各 Tracker 返回的 seeder/leecher 数相加。两个站点可能报告同一批 Peer，UI 无法凭这些人数判断交集。
- 证据：受控模型复现 A02，两个 Tracker 各返回 10，列表汇总显示 20。可以确认是相加；不能据此确定真实独立人数一定为 10 或 20。
- 建议：说明“Tracker 报告合计”，或保留逐 Tracker 数字、选取有明确含义的汇总策略。不要把合计标成精确独立人数。
- 位置：`src/domain/torrents.ts:153`。

## 低优先级边界

- 文件分页确实只分页渲染，3.00 仍一次返回该种子完整文件元数据。上千文件可正常使用已有虚拟列表；极大文件集或慢连接下，初次载入和刷新仍可能等待。筛选/排序在浏览器主线程执行，复杂正则也可能拖慢界面。这是实际体验边界，不是分页按钮失效。
- 自动刷新是真正的轮询；按一轮请求结束后再等待设置秒数，不能把“5 秒”理解为严格每 5 秒收到数据。当前磁盘查询也在串行刷新链中，慢磁盘会延长这一轮。关闭自动刷新后，底部数字保持上次快照，不是持续实时更新。
- 分块图是基于 3.00 完整分片位图的完成比例，聚合格最多 512；它不能显示某个尚未完成分片内部的逐字节下载百分比。位图长度异常时当前缺位会按未完成处理（诊断 A06），可增加长度校验；尚无证据证明正常 3.00 会返回这样的截断值。
- 3.00 与较新版本的分享率计算口径存在上游差异；当前 UI 显示 daemon 返回值，不应为了表面一致擅自重算。`wanted` 的 0/1 与布尔值已做归一化，不应将本轮实测的 `[1,0]` 当作故障。

## 封板处理建议

优先处理 1、2、3，避免操作对象和真实数据出现偏差；5、6、7 应同步澄清或修正显示/提交含义。4 属于多客户端同时编辑时的保护不足，应一并完善。无需因为这些问题整体取消 UI，也没有依据要求用户升级 3.00 来掩盖前端问题。

这份记录只评估、列出问题，不代表修复已经实施。当前环境与发布包保持不变。
