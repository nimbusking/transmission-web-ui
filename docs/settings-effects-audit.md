# 设置实际生效核验（2026-11-16）

后续修正：用户已授权针对F1/F2/F3开展优化，保存基线与自动模式显示现已修复；4.0.0提供风险处理和仅暂存关闭入口，并完成两端关闭uTP的新TCP实际限速对照。最新实现、69有效三浏览器/4真实场景及19081更新见[验证记录](validation.md)。以下保持修正前的审计事实和失败边界，其他未覆盖项继续开放。

结论：当前4.1.4的核心限速、下载队列、分享率/空闲停止及定时限速有真实行为证据，但三个设置页尚不能作为四版本完整封板通过。发现两项前端状态问题和4.0.0实际限速异常；其他版本的失败及网络能力未覆盖项必须保留。

## 方法与环境

使用19081当前同一生产资源快照，归档SHA256为`f1c811c689cec14d4da149d3a9bf262bbe1a3e4e0df6f0c536db916ca2bfd1c5`。在新建桥接网络中启动四版一次性daemon、本地tracker、做种及接收端，以自有64MiB私有任务验证；DHT/PEX/LPD/端口映射关闭，不使用公网种子。参数由实际生产页面保存，没有mock或拦截RPC；传输结果按真实daemon累计上传/下载字节差除以真实耗时测量，分钟级行为等待实际时间，不调整时钟。直接RPC仅用于准备/启停本次夹具和观察状态。

最终主运行是**1通过、3失败，5.5分钟**，不是四版全通过。中间验证和补测不累计成通过数。主脚本及浏览器用例保留在`.lab/settings-effects/`，原始日志`artifacts/settings-effects-run.log`、报告`.lab/settings-effects-report`；本轮未将这些实验脚本设为正式CI门禁。

## 发现的问题

1. **F1，保存后的脏状态残留。** 页面成功提交，daemon实际生效，但“未保存更改”计数和保存按钮可能仍保留。`SettingsDialog.vue`的`initialDaemon`是普通对象，`changes`依赖的响应式草稿在同值读回时不一定失效；保存中重算与随后更新基线的顺序还可能留下旧缓存。需要使基线响应式并在保存完成后可靠重算，补“保存→按钮禁用/计数清零→再编辑”的回归。本轮仅定位，未修复。
2. **F2，自动时段与弹窗状态不同步。** 4.1.4后端已自动进入备用限速，实际约32.8kB/s，长期打开的弹窗`alt-speed-enabled`勾选仍为false。草稿没有接入后端自动切换。需要区分当前生效状态与未保存草稿，同步状态时保留用户未保存的输入。本轮未修复。
3. **F3，4.0.0 uTP限速异常。** 两次UI设64的实验都约638kB/s；独立20秒持续采样约639kB/s，任务`honorsSessionLimits=true`，不能用启动突发解释。后续TCP对照未能在40秒内建立下载连接，因此没有证据保证关掉uTP即可解决。上游[4.0.6发布说明](https://github.com/transmission/transmission/releases/tag/4.0.6)及[PR 6551](https://github.com/transmission/transmission/pull/6551)记载uTP限速改进，支持将其列为daemon版本风险；本前端正确提交值不等于该版传输满足设置。
4. **F4，关闭队列不等于启动此前等待任务。** 4.1.4/4.0.6在关闭队列限制后，已有2个传输任务继续，另一个未立即传输；显式开始后3个都收到数据。应明确界面语义，不能暗中替用户启动其他任务；也不能把这个现象误写成队列上限1/2无效。

## 四版本结果与失败边界

| 版本 | 已观察效果 | 未通过/未执行 |
| --- | --- | --- |
| 3.00 | 上传/下载限速及关闭、下载队列1/2实际有效 | 关闭队列后再次开始未在40秒内达到3个传输任务；后续分享率/空闲/定时未执行 |
| 4.0.0 | uTP实际超速复现；单独UI改监听端口后新TCP端口可连、旧端口关闭 | TCP下载对照等待超时，后续核心矩阵未执行；加密补测因测试选项文字错误超时，未计整体通过 |

| 4.1.4 | 上表核心场景完成 | 跨午夜/排除星期/手动覆盖等扩展矩阵仍未验证 |

主运行保留3个失败；加密补测的测试定位问题没有作为产品缺陷。4.0.0监听端口仅为补测前段已成功断言，原始trace路径见[审计汇总](validation-evidence/settings-effects-audit.json)，不将整个补测记通过。真实数据和失败边界与历史`settings-compatibility.json`的“写入后读回”证据分别记录。
